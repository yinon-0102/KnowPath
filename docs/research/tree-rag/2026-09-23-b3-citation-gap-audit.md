# 合并测评的引用覆盖差异审查

对象：tree-b3-repair-40-v2/retry-two-extended-v1/merged.jsonl，40 题 × 3 模式，包含选择性重跑和两条延长超时记录。仅离线读取保存的响应及代码，未新增模型调用或修改业务逻辑。原始 freeze 校验通过。

“最终必要证据覆盖”实际衡量 response.sources，即模型输入上下文的原文区间覆盖；“引用必要证据覆盖”衡量 response.citations 中被引用叶子的原文区间覆盖。两者均不是答案正确率；引用整个叶子也不能证明回答完整表达了该叶子里的所有必要要点。

## 核对结果

- A 上下文覆盖 91.25%，引用覆盖 62.9167%；B3 上下文覆盖 90.8333%，引用覆盖 72.0833%。
- 32/40 题 A/B3 的 response.sources 列表逐字段完全相等，包含文本、元数据和顺序。
- 在这些完全相同上下文题中，引用覆盖差异对全 40 题宏平均净贡献 +8.75 个百分点；全体差异为 +9.1667 个百分点。这不能直接归因于树形检索，需固定输入重复生成和核验来评估稳定性。
- 第 7、14、20 题的 A 和 B3 上下文完全相同，必要证据均覆盖 100%；A 引用覆盖均为 0，B3 均为 100%。三题贡献全体差异中的 +7.5 个百分点。

| 题号 | A 的可观测降级原因 | B3 状态 |
|---|---|---|
| 07 | 核验 missing_points[] 字段类型错误，schema_fields/string_type | answered |
| 14 | 核验 claims 与检查项的引用关系未满足 citation_relationship | partial |
| 20 | 核验 claims 与检查项的引用关系未满足 citation_relationship | partial |

这三条 A trace 均记录 verification/safe_nonanswer_fallback。当前 verification.py 的保护逻辑在契约错误后返回 insufficient 和空 claims，以避免发布未经验证的文字。因此它们计为服务成功，但没有交付有效答案，不能解释为检索没有找到证据。

全体 A 有 5 条 safe_nonanswer_fallback（07、13、14、20、36），B3 有 2 条（09、13）。还不能仅凭日志断言全部校验规则错误；已证实的是共享生成/核验协议的稳定性影响最终结果，具体哪些响应可安全规范化、哪些应拒绝，需要最小复现进一步区分。

## 上下文覆盖为何略低

仅两题的上下文必要证据覆盖不同：第 09 题 A 为 100%、B3 为 50%；第 25 题 A 为 33.3333%、B3 为 66.6667%。宏平均相抵后 B3 为 -0.4167 个百分点。其余 38 题覆盖相同。

第 09 题双方重排联合 Recall@10 都是 100%，B3 最终上下文遗漏了 A 包含的必要叶子 a3ba97d…；该叶子在 B3 protocol_capacity.omitted_chunk_ids 中，不在 invalid_chunk_ids 中。后续已完成容量装配重放，具体原因和最小验证见下文。

第 25 题 B3 多保留了一段必要证据。第 17 题虽然 B3 重排联合 Recall@10 从 50% 提高到 100%，但双方最终上下文都已覆盖 100%，且上下文完全相同；排序收益未增加该题最终可用证据。

## 判断与后续建议

存在真实的中间环节损耗，但不能由引用覆盖更高推导出“B3 检索收益被后续全部掩盖”。当前多数引用差距出现在完全相同的上下文上，更直接指向生成/核验输出及契约降级差异。

优先对上述格式和引用契约失败建立最小复现，保留支持性检查，区分可无损规范化的格式问题和真实语义/引用错误；评测分开报告服务完成、契约降级、有效回答和人工正确性。之后固定相同上下文、统一超时、对所有预定条件重复生成，禁止只重跑低分答案。检索侧独立重放第 09、25 题上下文装配，解释必要证据取舍，再决定是否修改 B3。

离线诊断脚本：主工作区 .tmp/analyze_b3_citation_gap.py。未提交或推送。

## 继续审查：120 条重放和两项最小验证

脚本：主工作区 .tmp/b3_followup_audit.py；结果：.tmp/b3_followup_audit.json。读取 SQLite 使用 mode=ro 和 query_only，审计钩子禁止网络、子进程及 .env 读取。原冻结和延长超时派生冻结均验证通过。

### 1. 生成输入一致性比仅上下文一致更强

用冻结模型参数和真实请求构造器重建每题的首次生成请求体，32/40 题 A/B3 请求体哈希完全相同，包括问题、原文顺序、系统提示及请求选项。这些题对全体引用覆盖差异净贡献 +8.75 个百分点，占全体 +9.1667 个百分点的大部分。

这说明该差异主要来自相同输入之后的生成、修订、核验输出差异，不能归因于检索提供了不同证据。当前每条件主要只有一次有效执行且包含重跑，尚不能估计这种差异的可重复性；也没有证明远端模型行为变化的具体原因。

### 2. 第 09 题：片段级插入与整组装配的边界错位

120/120 条已保存上下文 ID、顺序、原文和完整 protocol_capacity 记录均被生产装配逻辑精确复现。

B3 第 09 题先选择第三十九条的两个片段，再选择第一百三十条定义组的两个片段。问题点名的第四十条排在第 5 个叶子；加入它后校验输入保守预算为 6,887 + 8,000 = 14,887，超过 14,000。

原有补救函数 preserve_baseline_with_anchors 将第四十条插在最后一个叶子之前，即 0 基索引 3。然而索引 2 与 3 同属第一百三十条定义组；装配扫描索引 2 时就会把两者一起放入。把第四十条放到索引 3 前并未使它先于完整定义组进入，补救第二遍的结果完全不变。

离线单变量探针只把插入位置移到最后完整组的起点（索引 2），沿用原文、依赖、14,000 预算和生产装配器，不使用金标准选择证据。结果第四十条成功进入，第 09 题上下文必要证据覆盖由 50% 变为 100%，校验规划预算为 5,772 + 8,000 = 13,772。金标准只用于选择结束后的覆盖评分。

这是已复现的片段级补救规则与原子组装配不一致。该探针不是正式修复，也不是新的在线结果；第 09 题改善不代表其它题不回退，需要全 40 题离线验证及单独冻结后再评测。

### 3. 后一轮契约失败清空上一轮已核验结论

真实 A 第 07 题第一轮已有 3 条结论通过校验并满足依赖；第 20 题第一轮已有 6 条。第二轮分别发生 missing_points 字段类型错误与 citation_relationship 不变量失败，最终均触发 safe_nonanswer_fallback，返回 0 条结论。

生产 AnswerVerifier 的最小注入复现：第一轮保留一条已核验结论、另有未解决要点；第二轮结构正常时返回 partial 和 1 条结论，只把第二轮 missing_points 改为错误对象类型时返回 insufficient 和 0 条结论。第一轮校验记录仍为 supported。该复现使用合成模型输出，仅验证程序分支，并非伪装成真实 API 结果。

保守拒绝发布第二轮未经验证的文字是正确的，但当前实现没有保留上一轮仍可用的已核验部分。后续修复应绑定同一问题、相同证据快照及依赖闭包，只保留此前通过验证且未被后续有效证据推翻的结论，不能简单采纳格式错误输出。

此外，所有 insufficient 统一显示“当前检索证据不足”，把契约失败与真实证据不足混为一谈；这是可观测性和用户解释缺陷。测评 service_success 仍会计为成功，所以 120/120 表示流程完成，并不代表全部回答有效或完整。

### 4. 仍未证实的部分与修复顺序

原始失败的 provider JSON 没有保留，现有日志只含脱敏错误分类。因此第 14、20 题不能进一步确定是重复检查、漏检查、引用集合不符等哪一条具体不变量触发，不能直接放宽规则。缺失引用身份也不能自动补成“有证据”。

建议先修复两项已复现行为：按完整依赖组边界执行显式锚点补救；保留上一轮可信部分并明确记录契约降级原因。对 A/B2/B3 共享路径一致生效，不修改金标准或只重跑低分答案。随后统一超时和重复次数重新比较，单独报告检索指标、契约成功率、有效回答状态及答案质量。

本轮仅审查、离线复现和更新报告，没有修改生产代码、重跑模型、提交或推送；所有既有测评数据未改。
