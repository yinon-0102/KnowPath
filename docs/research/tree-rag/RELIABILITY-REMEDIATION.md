# RAG 可靠性问题根因与修复方案（2026-09-21）

本文件保留基于已归档实验的分析，并在末尾记录后续修复与验证。
根因分析基线为本地分支 `codex/rag-foundation` 的 `451983e`，历史实验和人工标签不重写。
普通A与B1共用的模型调用、预算、核验和测试入口是当前优先修复范围。

## 已确认的问题与证据边界

| 问题 | 已确认的原因 | 尚不能断言的内容 |
|---|---|---|
| 大量集成测试跳过 | 专用测试环境变量缺失时fixture直接skip；多存储参数化扩大数量；无必跑测试清单和跳过阻断机制 | 不能由skip推断业务MySQL配置错误或服务连接失败 |
| 输入预算频繁超限 | 完整JSON的UTF-8字节数被作为token上界；上下文选择未为后续草稿、核验及修正请求做完整容量预留 | 37次历史预算失败缺少逐阶段记录，不能断言全部仅由计数偏大导致 |
| 无效模型响应 | API只请求JSON对象，业务字段、枚举、引用和依赖关系在返回后才验证；输出结构缺少与输出预算一致的大小限制 | 原12次失败未保存足够分类，无法认定全部是截断、模型幻觉或同一种schema错误 |
| 无收益的第二轮调用 | 只有完整answered提前结束；真实模型的insufficient/clarify会继续进入修正，即使现有证据不能补足 | 不能因此推断所有超时均由第二轮造成 |
| 超时与失败难定位 | 所有阶段共用总期限，未按下一阶段所需资源决定是否继续；外层超时缺少当前阶段；失败丢失先前局部trace | v4四次超时不能细分为网络、生成、核验或排队原因 |
| 核验后仍有条件遗漏疑点 | 引用存在、原文已召回、模型判supported并不证明限定条件完整；生成和核验使用同一模型，错误可能相关 | 同模型不是已证明的唯一原因，换模型也不保证正确 |

## 推荐路线

采用“隔离真实测试 + 全程诊断 + 模型适配预算 + 有界回答状态机”，先修公共链路，再比较A/B1。
保留已有范围、版本、引用、删除和未核验内容禁止发布的保护。

备选路线及取舍：仅提高输入/输出/超时上限改动少，但v4已说明不足以解决问题；直接换模型或增加树层级
会引入新变量，不能修复静默skip、错误单位、无效修正和失败trace丢失。换模型可作为后续独立开发实验。

### 1. 先消除“关键测试未执行也显示成功”

复用 `py/scripts/accept_learning_backend.py` 已有的一次性Docker容器、动态端口和受限清理机制，
将存储环境准备从付费模型验证中拆出。保留业务数据库配置，不把业务库地址自动当作测试地址。

定义三个可独立执行的验证入口：

1. 离线规则回归：允许明确的模拟服务，验证范围、引用、预算、并发发布和失败状态。
2. 真实存储集成：独立MySQL/Neo4j/Qdrant，执行迁移、事务锁、CAS、删除与故障恢复；不依赖模型凭据。
3. 真实模型验证：显式加载模型配置，调用真实embedding、重排、生成、核验，并运行开发评测。

每个入口保存预期用例集合、实际执行集合、通过/失败/不适用理由、服务及schema版本。
必跑用例缺环境、零执行、意外skip均返回非零；合法不适用的存储组合在测试矩阵中排除并单列。
不能为消除skip而让MySQL行锁用例在SQLite上假运行，也不能把慢速集成隐藏在普通回归通过数中。

### 2. 在新的真实调用之前补齐失败诊断

请求开始即建立独立于成功响应的调用记录，每个阶段发送前记录开始，在finally或超时终态记录结果。
包括阶段、物理调用序号、耗时、输入计数器版本、输入估算/真实用量、输出预留/真实用量、结束原因和明确错误类别。
保留已完成阶段，外层超时也能读到当前阶段；迟到调用不得改写已经发布的终态或发布答案。

分别标识连接/读取超时、429、5xx、JSON解析、schema字段、引用关系校验和输入预算错误。
记录校验错误类型及允许的字段位置，不能将错误值、原始供应商响应、密钥或URL带入公开错误详情。
业务API仅返回安全白名单信息，诊断记录按原有访问控制保存。

已返回合法usage时即记录；远端完成或账单不确定时保留unknown，不能按0费用处理。
费用预约与实际计费分别表示，历史没有记录的失败成本不回填猜测。

### 3. 统一模型预算，按完整调用协议组装证据

把模型实际上下文能力、应用输入上限、输出上限和金额限制分开；字节数明确标为字节上界。
为生成、核验、修正建立同源的计数profile：优先使用与部署模型匹配的供应商tokenizer/计数接口，
包含聊天模板开销并用实际usage校准。不能直接把OpenAI的tokenizer当作Qwen的精确计数器。
如果供应商未提供匹配的计数方式，保留显式保守模式和余量，承认精度限制，不能简单除以3当作精确值。

选取证据前，对系统提示、问题、完整证据组、草稿/核验结构、修正反馈和输出预留做容量规划。
紧凑化协议：请求内使用短ID映射到完整来源身份，要点文本只保留一份，成功核验返回ID/状态，
给claim数量、要点数量、理由长度设定与输出预算一致的约束；超过结构容量明确拆分或返回部分结果。
不靠裁掉条件、截断原文或将结构不足误报为资料不存在来节约预算。

### 4. 把“是否修正”改为明确的状态决策

| 首轮核验结果 | 后续动作 |
|---|---|
| 必要要点已完成且有支持 | 发布answered |
| 现有证据足够，但草稿遗漏或写错 | 资源充足时最多修正一次，再完整核验 |
| 确认当前证据不足且无可发布结论 | 发布insufficient；不再次要求同样证据生成新答案 |
| 确认对象不明、需要用户补充 | 发布clarify，不进行无意义修正 |
| 部分结论已核验通过，其他部分不可完成 | 依赖组完整时发布partial，保留已核验原文措辞，明确剩余缺口 |
| 核验服务、格式或引用契约失败 | 明确failed，不发布未经核验的正文 |

“证据不足”不能只相信生成器自述；必须经首次有效核验，或由空的合法检索结果等确定性条件支持。
区分answer_incomplete、evidence_missing、clarification_needed等原因，避免把预算不足、服务失败当成无答案。
启动第二轮前必须同时有输入、输出、调用次数、金额和剩余时间；只够生成、不够核验时不能启动修正。
分阶段时间预留依据测得的调用分布和部署目标确定，不把120秒直接改成600秒宣称修复。
评测继续禁止隐式重试；后续若引入明确可重试错误策略，必须单独冻结，并计算每次物理调用的费用与时间。

### 5. 加固结构化输出与条件核验

对具体供应商/模型版本探测严格schema能力；支持时使用版本化schema约束，仍执行本地身份、范围、依赖校验。
不支持时使用精简且有界的JSON协议，通过真实契约样本验证；不得假设json_object就保证业务schema。
格式修复若调用模型，必须计入原有最多2次生成/2次核验，且最终正文仍需核验，不叠加隐藏调用。

核验分别检查“原文是否支持结论”和“结论是否保留必要的主体、条件、例外、否定和量词”，
以可回查的证据跨度说明结果。已知并列条件、限定和跨页续文加入固定回归；模型识别结果仍是待检验输出。
检查清单不能仅沿用生成器自报要点；需要依据问题和证据检查遗漏，同时避免凭想象扩大必答范围。
不同模型/提示的独立核验作为开发集对照选项，以实际漏检率、延迟和费用决定，不能宣称换模型就可靠。

## 顺序和验收

1. 先完成诊断与测试门禁，确保下一次失败能定位、关键集成确实执行。
2. 修正计数/协议容量和无效第二轮，将已确认缺陷建立能先失败后通过的回归。
3. 验证严格schema能力和条件保留，仍不能靠模型自评代替人工语义评分。
4. 预先固定修复验证样本与重复次数，随后重跑完整40题A/B1开发集；保留全部失败和物理调用记录。
5. 满足真实服务稳定性目标、人工标签及部署费用/延迟门槛后重新冻结，最后运行保留集。

确定性验收：必跑集成无意外skip；阶段失败均可分类；空答案无效修正回归通过；
完整证据组与引用/范围/版本保护全部通过；任何未核验正文不能因超时或格式恢复发布。
模型验收：分别报告服务成功、证据不足、部分完成和人工任务成功；重复次数及稳定性目标在新运行前设定。
一次成功或少量失败题改善不足以证明生产可靠。未达到目标则不切换默认配置，不为通过而降低证据要求。

没有已审核的qwen-plus tokenizer部署映射；当前仍用带余量的UTF-8字节保守上界并记录实际usage，
不声称计数精确。时间与金额预约也不是供应商取消或账单保证。

真实复测额外发现了两层定位协议缺陷：模型先把10字原文的字符偏移写成12；改成精确摘录后，
又会合并PDF“原\n则”的换行。最终使用本地预分配的 `segment-id-v1`：模型只选段ID，
本地恢复原始跨度，不去空白、不模糊匹配。所有原文片段按原顺序完整提供并计入预算。
该转换只负责定位，不代表段内所有语义均被模型正确理解。
