## 拖慢聊天的具体路径

1. **当前默认路径：模型生成占主要时间。** `learning/rag/runtime.py:390` 默认 legacy；该路径检索后执行一次 generate_json，再进行本地校验，没有额外的大模型校验轮次。普通聊天由 API 的后台任务直接启动，不等待导入 worker 的 2 秒队列轮询。
2. **正文没有真正边生成边展示。** `learning/conversations/service.py:380` 在完整答案生成和校验后才拆成 256 字符的 message.delta。本次两个成功样本的首段正文和完整回答仅相差约 0.00005–0.00006 秒，符合缓冲后一次返回的行为。`frontend/src/api.js:107` 的 readMessage 也只采纳 message.completed；但实际浏览器入口未在本次 HTTP 测试中验证。
3. **历史增强 RAG：生成 + 大模型核验 + 返工。** 2026-09-21 的 80 次实测中，生成累计占 40.4%，核验占 55.4%，合计 95.8%。成功的两次模型调用样本中位数约 15.9 秒，四次调用样本约 53.3 秒。四次调用既包含修订，也包含校验响应结构失败后的重复执行。该结果适用于对应增强 RAG 评测，不适用于今天默认 legacy 模式。

历史证据：`docs/research/tree-rag/evaluation/runs/2026-09-21-reliability-dev-v8/dev.jsonl`，80 次调用总墙钟时间约 3733.3 秒，生成 1508.32 秒、核验 2067.39 秒；整体中位数 33.743 秒，成功样本 68 次。此前将这些几十秒的数据泛称为普通聊天速度，口径需要纠正。

## 后续优化顺序（尚未实施）

1. 先明确记录本地答案校验失败原因，仅记录原因枚举与计数，避免记录资料正文。第三次失败需要可定位的原因；三个样本不足以估计系统失败率。
2. 改善首字体验需要真正的模型流式输出和前端增量展示，同时设计最终引用校验及失败时的呈现方式，不能只把现有最终答案拆得更碎。流式展示主要改善等待体验，不自动减少总生成时间。
3. 对当前默认聊天，使用固定题集比较模型、上下文规模与回答质量，再决定提速策略；本次检索不是优先瓶颈。深度思考已关闭，不能再把关闭它当作新增优化。
4. 对增强 RAG，优先减少不必要的重复生成/核验和修复结构错误导致的重跑，同时保留必要的事实校验。
5. 对导入，下一步细分 Neo4j 首次连接、约束检查、写入、回读的时间，并做冷/热进程对照。本次不支持把所有慢都归因于向量生成或排队。
