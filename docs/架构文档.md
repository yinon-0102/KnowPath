# Keel Learning 后端架构设计

版本：v0.1-draft  
日期：2026-09-17  
定位：基于 Keel Agent Runtime 的个人学习与技能成长助手

性质：待评审的后端设计，非已实现功能清单。配套接口见 [API.md](API.md)。产品名称暂定为 Keel Learning，基础项目正式名称为 Keel。

已确认：用户自带资料、选主题后诊断、保留学习知识图谱、删除 CLI 与系统操作工具、同时保留资料知识和学习者状态更新；知识图谱采用 Neo4j，业务数据库采用 MySQL，向量检索采用 Qdrant。设计默认值：本地单用户服务、FastAPI、REST/SSE 和下文算法阈值；这些是可调整的实现选择，不代表用户已逐项确认。前端和考试备考不属于本次实现范围。

## 1. 设计结论

Keel Learning 面向普通用户的自有学习资料。用户导入 PDF、Markdown 或 TXT，选择要学习的主题，系统根据资料内容和用户的学习证据生成学习安排，并通过练习和复测更新后续计划。

第一版的业务闭环是：

```text
资料导入
  → 主题和知识关系构建
  → 用户选择学习范围
  → 初始诊断
  → 掌握度估计
  → 个性化学习安排
  → 讲解与练习
  → 复测与验证
  → 更新知识图谱和学习者状态
```

产品可以面向广泛的个人学习需求，但首版实验和演示需要使用固定资料与固定任务，才能和基线方案进行公平比较。

## 2. 首版范围与非目标

### 2.1 首版范围

- 单用户、本地运行；
- 支持文本型 PDF、Markdown、TXT；
- 一个学习空间关联一组资料和一个学习目标；
- 用户选择一个或多个主题作为本轮学习范围；
- 自动建立章节、知识点和前置关系；
- 生成 5—10 道初始诊断题；
- 保存答题证据并更新知识点掌握度；
- 生成 3—5 次学习任务；
- 支持资料依据的讲解、练习、提交和复测；
- 资料知识和学习者状态均支持版本化更新；
- 客观检查优先，模型判断作为开放题的补充；
- 通过 REST API 和 SSE 提供后端能力，前端可以后续替换。

### 2.2 首版明确不做

- 扫描 PDF、OCR、图片、音频和视频解析；
- 完整考试题库、考试排名和分数预测；
- 多用户账号、组织权限和在线计费；
- 日历、社交学习和教师后台；
- 性格、智力或“视觉型学习者”等心理画像；
- 对外开放任意 Shell、代码编辑或系统文件操作；
- 跨资料自动融合全部同名知识点、自动迁移所有旧计划；首版仍完整支持同一资料的新旧版本比较、人工确认和受影响状态重建；
- 训练新的基础大模型。

## 3. 架构原则

1. **领域状态与对话记忆分离。** 掌握度、答题记录和计划状态必须可查询、可计算、可追溯，不能只依赖 LLM 召回对话。
2. **知识内容与用户状态分离。** 教材事实、知识关系和用户掌握程度属于不同类型的数据，更新规则不同。
3. **证据优先。** 每个知识点状态、题目答案和重要解释都尽量关联资料片段、题目记录或用户确认。
4. **确定性检查优先。** 能用规则、解析器或计算工具判断的内容，不交给模型自由判断。
5. **可替换运行时。** 业务层依赖 Agent、Memory、Context、Verify 的稳定接口，不直接依赖 CLI 实现。
6. **最小权限。** 学习业务只开放资料解析、检索、出题、判分和计划工具，不继承 Keel 的任意命令执行权限。
7. **可验证的算法贡献。** 每项新增策略都要有基线、消融实验和可复现指标。

### 4.1 Keel Runtime 保留范围

保留或改造以下部分：

- `my_agent_llms/core/agent.py`：Agent 生命周期、系统提示词和统一收尾；
- `my_agent_llms/core/llm.py`：多厂商 LLM 客户端；
- `my_agent_llms/core/message.py`、`core/hooks.py`：消息和钩子；
- `my_agent_llms/agents/function_call_agent.py`：提取工具调用循环，保留与传输层无关的文本、工具、取消事件接口；删除终端展示耦合和 TDD/文件操作分支；
- `my_agent_llms/tools/base.py`、`tools/registry.py`、`tools/chain.py`：业务工具协议和注册机制；
- `my_agent_llms/memory/`：分层记忆、语义索引、冲突处理和来源追踪；
- `my_agent_llms/context/engine.py`：相关性、去重和 token 预算编排；
- `my_agent_llms/verify/`：借鉴验证、重试和停止控制；删除 `command_ok` 子进程执行分支，新增来源、题目与计划校验器；
- `my_agent_llms/planning/`：计划状态的通用能力；
- `my_agent_llms/bench/`：作为评测基础改造成学习任务离线评测工具；原代码任务用例不等于学习评测集。

基座核对版本为 `01322ef`。现有知识图谱主要服务事实冲突消解，并非课程依赖图；`TodoStore` 是进程内清单，不是持久化计划库；现有 Verify 的触发与副作用工具关联，不能直接覆盖学习问答。其 `semantic_support` 检查器尚未实现，`judge` 仅返回 PASS/FAIL，也不是带证据的教育评分器。以上能力均需显式适配，不标为开箱即用。源代码中的测试不能代替裁剪后的回归验证。

### 4.2 产品中移除的部分

- `my_agent_llms/cli/`、`chat.py` 和终端审批、渲染、输入历史等逻辑；
- `BashTool` 以及任何任意 Shell 执行能力；
- 面向代码改动的 `WriteFile`、`EditFile`、通用目录浏览和通用代码搜索工具；
- 依赖本地代码工作区的 `Workspace` 安全模型；资料导入改由受控的 `MaterialService` 处理。

`Tool` 和 `ToolRegistry` 不是命令行功能，仍作为 Agent Runtime 的内部扩展点保留。学习产品只注册白名单业务工具。

原 `tdd/`、Shell/文件检查器及相关代码任务测试退出新产品运行路径；先记录基座版本并在独立开发分支裁剪，再移除仅服务已删除功能的依赖。不要删除仍服务运行时能力的测试。资料上传在服务入口完成，不通过 Agent 任意路径读取。当前文档交付不实际删除或修改 Keel 源码。

## 5. 领域模型

### 5.1 核心实体

```text
Material
  └─ MaterialVersion
       └─ SourceChunk
            └─ TopicNode / KnowledgeRelation

LearningSpace
  ├─ selected TopicNode
  ├─ LearnerProfile
  ├─ LearnerState
  ├─ Assessment / Attempt
  ├─ StudyPlan / StudyTask
  └─ Evidence
```

#### Material / MaterialVersion / SourceChunk

- `Material` 是用户看到的资料；
- `MaterialVersion` 是一次导入或重新导入的不可变版本；
- `SourceChunk` 是带页码、段落或行号的原文片段；
- 日常停用使用归档，保留历史证据；用户要求彻底删除时提供独立清除操作，级联清除相关派生记录、文件、索引与记忆，并明确对学习空间的影响。

#### TopicNode

知识点节点至少包含：

```text
id（同一资料内的稳定概念 ID）, revision_id（不可变版本）,
name, description, material_version_id, graph_version,
source_chunk_ids, level, status, confidence,
created_at, recorded_at, valid_from, valid_to
```

#### KnowledgeRelation

首版支持：

```text
contains
prerequisite_of
related_to
assessed_by
explained_by
supersedes
contradicts
```

每条关系需要记录来源、版本、置信度和有效时间。新资料或用户纠正不会直接删除旧关系，而是建立新关系并把旧关系标记为 `superseded` 或 `inactive`。

另记录关系 `status=pending/active/rejected/superseded`。模型提取的前置关系默认是候选，需要来源支持并通过无环检查才可参与排课；无充分依据的关系待用户确认。同名不代表同一概念；不同资料默认不同命名空间。无真实生效日期的资料只记录登记时间，不把上传时间解释成知识真实成立时间。数值置信度是启发式评分，未经校准不得称为真实概率。

#### LearnerProfile

只保存与学习决策有关的信息：

- 学习目标；
- 可投入时间；
- 目标日期（可选）；
- 讲解和练习偏好；
- 用户主动确认的基础信息。

每个字段都要区分 `explicit`（用户明确提供）和 `inferred`（系统推断），并支持查看、修改和删除。

#### LearnerState

按知识点记录动态状态：

```text
topic_id
mastery_score       0..1
score_validity      current / stale / unverified
status              unseen / learning / unstable / mastered / needs_review
evidence_ids
error_tags
last_assessed_at
next_review_at
state_version
topic_revision_id, policy_version, independent_evidence_count
```

掌握度是派生状态，原始答题和复测记录必须作为不可变证据保存。

## 6. 两条知识更新管线

### 6.1 资料知识更新

```text
上传新资料或新版本
  → 解析为 SourceChunk
  → 提取章节、知识点和关系候选
  → 与现有图谱去重和冲突检测
  → 关联来源和版本
  → 写入新节点/关系
  → 标记被取代内容
  → 重建受影响的语义索引
```

候选知识由模型提取，但以下动作必须由规则或稳定逻辑完成：

- 资料版本和来源登记；
- 节点和关系的唯一标识；
- 旧版本失效标记；
- 同一资料重复导入的幂等处理；
- 受影响学习空间的重新评估提示。

### 6.2 学习者状态更新

```text
诊断/练习提交
  → 记录 Attempt
  → 生成 Evidence
  → 题目和答案检查
  → 按证据更新知识点状态
  → 找出受影响的前置/后继知识点
  → 调整 StudyPlan
  → 安排复测
```

资料知识更新不能自动改变用户掌握度；用户状态更新也不能修改教材事实。两条管线通过 `source_chunk_id`、`topic_id` 和 `evidence_id` 关联。

### 6.3 新版本发布与影响处理

1. 新版本在暂存区完整解析，计算内容哈希，生成节点/关系差异和冲突候选；失败时旧发布版本保持可用。
2. 完全相同的片段沿用概念 ID；有实质变化的内容建立新 revision。模糊的合并、替代关系需人工确认，不能因上传较晚就判为更正确。
3. 将已确认快照按版本写入 Neo4j，并构建该版本向量索引；两者就绪后，在 MySQL 事务中发布版本指针，旧快照不可变。跨存储同步不宣称为单一数据库事务。冲突未解决的断言不参与自动出题和判分。
4. 学习空间固定引用资料/图谱快照，不随最新版本自动切换。显示影响预览，用户确认后更新绑定。
5. 未变化知识点可继续使用已有有效证据；变化知识点保留旧成绩，但标记 `score_validity=stale`、`status=needs_review`，不能再据此跳过学习。
6. 旧题目留在旧版本下供历史查看，停止分配给新版本任务。正在进行的旧测验可按旧标准完成；成绩不能写入新 revision 的掌握度。
7. 受影响计划标记 `needs_replan`，只重排相关任务。删除的知识点退出新计划；新增知识点状态为 `unseen`。

用户纠正先建立提案，预览受影响节点和学习空间，确认后发布新图谱版本。资料中的“自称已掌握”、用户口头反馈都不能直接替代测验证据。

## 7. 核心算法设计

### 7.1 主题范围感知检索

当前问题进入 Context Engine 前，先经过学习范围过滤：

1. 过滤不属于当前学习空间或已排除主题的片段；
2. 加入选中主题的前置知识和相关证据；
3. 使用语义相关性、主题关系、资料来源权威性和当前薄弱程度排序；
4. 通过 Keel 的去重和 token 预算选择最终上下文；
5. 为每条关键结论保留来源片段。

目标不是把更多资料放入上下文，而是在固定预算下提高相关信息比例和来源准确率。

### 7.2 证据加权掌握度估计

掌握度由多次证据共同决定，不允许“一次答对即判定掌握”。输入包括：

- 题目所属知识点；
- 题目难度和题型；
- 是否独立完成；
- 客观判分或开放题评分；
- 错误标签；
- 与上次复测的时间间隔；
- 资料版本和评分标准版本。

首版采用可解释的加权证据均值，规则版本为 `mastery-v1`：同一知识点从当前 revision 选取最近 20 个不同题目族的有效、独立作答，每个题目族仅保留首次有效提交。一次提交中修改答案不重复计分；查看答案或提示后的作答用于教学反馈，不作为独立掌握证据。

设每条评分为 `s_i∈[0,1]`，权重 `w_i=评分可信权重×题型覆盖权重`，则 `mastery_score=Σ(w_i×s_i)/Σw_i`；无有效证据时分数为 null，不默认为 0。初版权重均为 1，开放题未经可靠判定则不进入计算。难度只用于组卷配额，不直接放大未经校准的“难题”权重。聚合覆盖至少 3 个不同题目族、至少 2 次测验，其中一次间隔至少 24 小时且包含应用题，分数 ≥0.8 才可标记 `mastered`；证据不足保持 `learning`。已掌握后有效分数降至 0.8 以下标记 `unstable`；到复习日期或资料变更则标记 `needs_review`，不把时间流逝直接作为答错证据。

以上数字是首版工程策略，必须写入可配置规则并通过试点评估；分数不是经过验证的认知能力或“掌握概率”。任何公开展示都附带有效证据数量与评分规则版本。后续可比较 BKT/Elo 等方法，但不得预先承诺优于它们。

### 7.3 约束感知学习计划

计划生成同时考虑：

- 知识点前置关系；
- 当前掌握度和错误类型；
- 每次学习时长；
- 目标日期；
- 复习间隔；
- 用户跳过或确认的内容。

计划调整采用局部重排：某个知识点失败时优先调整该节点及其依赖关系，不无条件重建全部计划。每个计划任务必须能说明生成原因。

首版先按有效前置关系作拓扑排序，再按“到期复习、薄弱点、未学内容”排序；同类候选按相关错误次数和最近评估时间排序。每次任务按预计分钟数装入用户时间预算；无前置满足项时优先安排前置诊断。估计时长不等于实际学习时长。超时预算、依赖成环或所选范围缺少必要前置时返回明确约束冲突，不能自行扩大学习范围。复习默认间隔 1、3、7 天，属于待评估调度规则，不宣称已建成个性化遗忘曲线。

### 7.4 学习验证层级

检查优先级如下：

1. 规则检查：选项、数值、格式、知识点覆盖；
2. 结构化检查：答案字段、引用片段、题目难度和映射关系；
3. 关系检查：前置知识是否满足、结论是否超出资料范围；
4. 语义检查：开放题是否支持题目要求；
5. LLM Judge：仅作为无法确定时的补充，并保存评分依据。

验证失败时返回具体原因，例如“缺少资料依据”“前置知识未掌握”“答案只复述原题”，供计划模块生成补救任务。

必须分开三种验证：题目/解释是否可靠、学生本次答案是否符合评分标准、长期学习效果是否提升。Agent 的 Verify 只可重试系统生成的题目和讲解（默认最多 2 次修正），不得替学生改写答案直到通过，更不能因模型内容验证成功而提高学生掌握度。首版题型仅单选和短答；单选按答案键判分，短答按预先冻结的评分要点与原文评分，存在歧义时标记 unverified 并安排替代客观题。评估中不得向学生泄露答案键、评分要点或直接暴露包含答案的来源原文；提交完成后再开放解析与定位。

## 8. Keel 记忆机制的领域化使用

| Keel 层 | 学习助手用途 | 是否作为学习状态真相 |
|---|---|---|
| L0 Playbook | 稳定目标、时间约束、讲解偏好 | 否，需同步到结构化 Profile |
| L1 Working | 当前学习会话 | 否，属于临时上下文 |
| L2 Summary | 阶段性学习总结 | 否，作为辅助摘要 |
| 冷存储思想 + 独立领域事件表 | 不可变答题、评分、版本事件；不直接当普通对话写入 | 领域事件表是真相，Keel 对话冷存储不是 |
| 语义索引 | 检索资料片段和历史证据 | 否，索引可重建 |
| 冲突处理 | 资料版本和用户纠正 | 关系更新依据之一 |
| 知识图谱 | 资料知识和前置关系 | 是，需带来源和版本 |

模型不能通过通用 `remember` 工具写入掌握度。只有评分服务能登记有效证据，只有 MasteryEstimator 能按规则计算状态；Agent 可以请求读取或触发评估，不能提交自拟成绩。用户主动修改的目标与偏好由 Profile 表持久化；Memory 仅缓存可重建摘要，过期摘要不得覆盖结构化真相。

## 9. 业务工具白名单

首版业务服务如下，其中只有只读/受控生成类能力可以注册为 Agent 工具：

- `import_material`：由上传 API 触发的服务，不开放模型指定磁盘路径；
- `search_material`：在学习范围内检索资料片段；
- `get_topic_graph`：读取主题和前置关系；
- `generate_assessment`：根据范围和覆盖要求生成诊断或练习；
- `grade_attempt`：调用确定性规则和必要的语义评分；
- `record_learning_evidence`：仅评分服务事务调用，不作为模型自由调用工具；
- `build_or_update_plan`：生成或局部调整计划；
- `get_progress`：读取结构化学习状态。

所有工具都应有输入校验、超时和可追踪的 `run_id`。不注册 Bash、文件编辑和任意外部网络工具。

建议的领域接口：`MaterialParser.parse(blob)->chunks`、`GraphService.stage/publish`、`AssessmentService.generate/grade`、`MasteryEstimator.apply(evidence)->state`、`PlanService.build/replan`、`LearningContextBuilder.build(scope,state,query)`。接口均传入服务端解析的 space_id 和版本快照，不能接受模型自行切换学习空间。API DTO 使用 Pydantic 校验，Agent 工具的文本返回值不能作为未经校验的数据库写入对象。

## 10. 持久化与一致性

MySQL（InnoDB、utf8mb4）作为业务记录和版本发布状态的权威数据库，保存：

- 资料元数据和版本；
- 图谱快照登记、抽取及纠正事件、来源映射（图谱节点与关系由 Neo4j 承担）；
- 学习空间和学习者模型；
- 诊断、题目、答题和证据；
- 计划、学习任务和状态变更事件。

原始资料和导出文件存放在受控资料目录。Neo4j 保存知识点版本、章节、来源关联和前置/替代/冲突关系，并执行路径与依赖查询；掌握度、答题和计划仍在 MySQL，不复制成另一套可独立修改的图谱状态。对掌握度和计划采用“追加事件 + 当前派生状态”的方式，更新带有 `state_version`，避免重复提交覆盖较新的状态。

Qdrant 通过独立 VectorBackend 适配器接入；这是新增组件，不是 Keel 当前已具备的组件。原 Keel 的 SQLiteVectorBackend 将向量存为 BLOB，并在启动时全量加载到 Python 内存做余弦排序，无 embedder 时退化为 TF-IDF，不是独立的向量检索数据库。迁移时保留其后端协议思想，增加资料版本与空间过滤，不能只替换连接字符串。

Qdrant collection 保存资料片段或允许检索的记忆向量，以及 chunk_id/material_version_id/graph_version/space_id/topic_id/content_hash/embedding_model 等 payload 过滤字段；正文与权威来源从 MySQL 读取，知识关系从 Neo4j 补充。题目答案键不进入通用向量索引。Embedding 模型与向量库是不同组件，模型尚未选型；须固定模型版本、向量维度和距离度量，换模型重建 Qdrant collection，不能混用向量空间。Qdrant 的 collection、payload 索引、快照和备份策略在实现阶段固化。

MySQL 最小表集合：`materials/material_versions/chunks`、`graph_snapshots/graph_change_events`、`learning_spaces/space_material_bindings/profiles/scopes`、`assessments/questions/submissions/grades/evidence`、`learner_states/plans/plan_tasks/sessions`、`runs/run_events/change_events/idempotency_keys/outbox_events`。Neo4j 实现 MaterialVersion、TopicRevision、SourceChunkRef 等节点及其关系，设置业务 ID 唯一约束，查询必须限定资料/图谱版本。题目答案键和内部评分标准不进入公共 DTO 或通用对话索引。

跨存储采用 MySQL outbox 事件和幂等 worker：先登记待处理版本与事件，再写 Neo4j 和向量库，以稳定对象 ID 去重；全部准备完成才发布 MySQL 版本指针。读请求固定到已发布版本；失败保留旧版并重试，禁止半成品进入出题。MySQL 保存可重放的图谱变更事件以便恢复。删除先写不可读标记，再清除图谱、向量和文件，全部成功后标记清除完成。无跨库分布式事务，不把失败后的部分清除报告为成功。

Keel 的 Playbook、事实图谱和记忆冷存储也存在 SQLite 耦合，须分别迁移到 MySQL 记忆仓储和 Neo4j 图谱适配器，不能保留与新存储并行更新的第二套权威数据。

单次有效评分登记 evidence 与更新 LearnerState 在同一事务完成；唯一约束是 evidence_id、submission_id+grading_version、space_id+topic_revision_id+policy_version。失效评分通过撤销事件和状态重算处理，不直接篡改历史。计划重排是独立异步任务，携带所依据的 state/scope/graph 版本，旧任务不得覆盖新状态。

后端建议 FastAPI（Python ≥3.13）+ MySQL + Neo4j + Qdrant + 受限后台 worker。MySQL 访问建议 SQLAlchemy 2.x 与 Alembic，Neo4j 使用官方 Python Driver，Qdrant 使用官方 Python Client；具体版本在依赖锁文件中固定。耗时 LLM/解析任务在 worker 执行，不阻塞 HTTP 事件循环；每个学习空间串行提交状态更新。首版应用单进程、并行任务上限 2、每个模型请求超时 60 秒、每个 run 最长 10 分钟，支持协作取消。重启后 running 标记为 interrupted/failed，事务外未发布结果不对外可见；按 run 类型安全重试，证据去重约束避免重复计分。SSE 事件持久化 7 天，最终状态由 MySQL 查询获得。

## 11. 安全和隐私

- 默认本地单用户，不把资料暴露给其他学习空间；
- 资料路径只能位于应用配置的资料目录；
- 不执行模型生成的 Shell；
- 限制单文件大小、页数和解析耗时；
- 首版默认单文件 20 MiB、文本 PDF 最多 300 页、每个空间最多 5 份资料；空提取或扫描件返回明确不支持，不能静默创建空知识库；
- 默认绑定 127.0.0.1，不开放公网；浏览器跨域仅允许配置的本地来源，写请求验证本地会话令牌与 Origin。此令牌不等同多人账号系统；
- 资料内容视为待分析数据，不能通过其中的指令修改系统提示、工具权限、评分标准或学习空间范围；
- 记录调用的模型提供商和资料是否发送到外部 API；
- 用户可以导出或删除资料、学习记录和画像字段；
- 题目、答案和资料引用不包含不必要的个人敏感信息；
- 使用朋友的 Keel 代码时保留 MIT LICENSE 和版权声明，并在参赛材料中说明基础代码与新增代码的边界。

## 12. 失败处理

| 失败情况 | 后端行为 |
|---|---|
| 资料解析失败 | 保留资料记录，返回可读错误，不创建半成品知识图谱 |
| 主题提取不可靠 | 标记为 `needs_review`，允许用户手动确认或重新提取 |
| LLM 不可用 | 允许浏览已建立的资料和状态；不能伪造题目或掌握度 |
| 开放题无法稳定评分 | 标记 `unverified`，安排客观题或人工确认 |
| 资料版本冲突 | 保留双方来源，标记冲突，不自动选择无依据的答案 |
| 重复提交 | 使用幂等键和版本号，避免重复写入证据或计划 |
| 计划无法满足约束 | 返回原因和可选放宽条件，不生成看似完整但不可执行的计划 |

## 13. 评测和参赛证据

离线评测至少包含：

- 资料片段检索准确率和引用准确率；
- 知识点覆盖率；
- 题目与资料一致性；
- 答案判定准确率；
- 重复错误率；
- 前后测成绩变化；
- 计划完成率；
- 达到目标所需学习时长；
- 单次任务 token、调用次数和耗时。

推荐设置三组基线：

1. 直接资料问答；
2. 普通检索 + 固定学习计划；
3. 主题图谱 + 学习者状态 + 自适应计划。

再分别关闭主题图谱、状态更新和计划调整，做消融实验。参赛材料中必须说明资料来源、模型版本、提示词或配置、测试集构造方法和失败样例。

生成的训练/练习题不能同时充当唯一效果测试。保留人工核验、难度匹配的独立前后测与延迟测；同一模型、资料、时间/调用预算下比较基线，报告样本数与局限。一月试点只能支持短期学习效果观察，不能宣称已证明长期认知提升。

## 15. 当前设计决策

- 运行形态：首版本地单用户；
- 存储：MySQL 业务数据 + Neo4j 知识图谱 + Qdrant 向量检索；Embedding 模型仍需单独选型；
- 接口形态：REST JSON + SSE；
- 学习目标：资料知识掌握，不做考试评分；
- 资料类型：文本型 PDF、Markdown、TXT；
- 知识更新：资料知识更新和学习者状态更新同时保留，但使用两条管线；
- 图谱策略：保留 Keel 的时态、来源和冲突处理思想，新增学习领域节点和关系；
- Agent：保留一个经过裁剪的 Function Calling Agent，不在首版同时维护五种 Agent 范式；
- 安全边界：不执行任意 Shell，不开放通用代码操作；
- 评测重点：在相同模型和固定预算下验证检索、掌握度估计和计划调整的收益。

文档评审重点：默认本地服务是否符合使用目标、学习评分阈值是否适合试点资料、知识更新影响预览是否足够。评审不阻塞本次文档交付；确认后再进入代码改造和实现计划。
